## 1. 주제별 멘토 답변

### 1-1. 설계 원칙 — 정합성 우선, 성능은 그다음

_관련 준비 질문: 1차 1순위(Redis Lua 병목)_

- 속도·성능도 중요하지만 **데이터 정합성을 맞추는 게 1순위**, 그다음 성능 개선.
- Lua로 정합성은 맞췄으나 성능이 안 나올 때를 대비하는 거라면 → 테스트해보고 **목표치에 도달하지 못했을 때** Lua 말고 원자적으로 해결 가능한 다른 방법을 찾는다.
- 현재로서는 Lua 자체가 병목이다/아니다 말하기 어려움.
- **판단 기준:** 우리가 개발하는 시스템의 **목표치**를 정하고, 그 성능에 도달하지 못하는 원인이 Lua 내부 실행에서 실행되는 것들의 이슈라고 판단되면 그때 다른 기술을 고려.

### 1-2. Redis-DB 정합성 / 장애 대응 조합

_관련 준비 질문: 1차 2순위 · 2차 4번(정합성 깨졌을 때 조합)_

팀원들은 Redis 상태를 나누어 관리하겠다고 함. 이 상태에서 Kafka/DB 이슈로 해당 상태를 업데이트하지 못했을 때 대응 (정답은 없고 아래를 조합):

- **스케줄링에서 작업**하는 방법.
- Kafka 메시지 발행 실패를 **감지해서 재처리하는 로직** 제작.
- 스케줄링으로 **데이터 정합성을 계속 체크**해서 작업.
- 에러 발생 시 **모니터링 알림을 받아 수동으로 재처리할 수 있는 API** 마련.

### 1-3. 트래픽 스파이크 / 대기열은 맨 앞단

_관련 준비 질문: 1차 4순위(트래픽 스파이크)_

- **대기열을 앞에 두는 게 맞다.** DB도 있고 Redis도 있고 DB 자체를 2개 사용하는 상태인데, 중간에 넣으면 정합성 맞추기가 더 힘듦. **트랜잭션이 발생하기 전에 미리 방어선**을 두는 게 맞음. 안 그러면 중간에 터졌을 때 **보상 트랜잭션 처리가 더 어려움.**
- 대기열을 맨 앞에 두고, 대기열이 너무 몰려 시스템에 부하가 가면 → 수치를 100까지 했다가 어느 정도 병목이 풀리면 1000으로 늘리는 식으로 **limit(제한)을 유동적으로 관리**할 수 있게끔 만드는 것도 하나의 방법.

### 1-4. 병목 지점 파악

_관련 준비 질문: 1차 5순위(전체 시스템의 다음 병목)_

- 보통 **DB의 CPU/메모리**가 못 버티는데, 이것도 테스트하면서 잡아야 함.
- **시작부터 끝까지 한 번씩 부하를 흘려보면서** 어느 지점에서 CPU/메모리가 부하되는지 찾고, DB 이슈면 **DB 스펙을 늘려가며** 우리가 준 부하만큼 받아주는지 계속 확인하며 그 수치를 찾음.
- 후보 중 어디에 병목이 가장 많이 나온다고 말하긴 어렵고, 보통 DB에서 부하가 많이 나오므로 **Redis라는 2차 DB를 사용해 함께 개선**. 하드웨어 스펙이 낮으면 CPU/메모리 이슈 등 여러 병목 포인트가 있을 수 있어 확인 필요.

### 1-5. 동시성 제어 / DB락

_관련 준비 질문: 1차 9순위(동시 상태 변경 처리) · 2차 3번(Redis 원자성+Kafka 순서 vs DB락)_

- 멘토는 실무에서 DB락을 사용한 적이 없어 DB락 자체에 대한 의견보다는, **DB락을 고민한 이유가 "동시에 요청이 들어왔을 때 정합성을 어떻게 맞출지"인지**를 확인.
- Kafka 처리 전 동시성 이슈는 → **메시지를 보내기 전에 Redis의 원자성을 이용해 동시성 이슈를 해결**하고, **순서가 보장될 수 있는 메시지를 발행해 순차 처리**하는 방식으로 해결 (멘토님도 이 방식으로 문제를 해결).
- 멘토는 DB락으로 동시성 처리를 해본 적이 없어 DB락에 대한 의견을 말하기는 어려움.
- 설계한 것처럼 **Redis로 원자성을 보장해놓고 이 순서가 뒤바뀌지 않도록 메시지 순서 처리**를 구현하면 동시성 제어는 충분히 가능.
- **DB락을 사용해 개발해도 되며**, 이렇게 개발해서 완성하면 멘토가 따로 DB락에 대해 확인해보고 의견을 줄 수 있음.

### 1-6. 대기열 UX / 새로고침

_관련 준비 질문: 1차 10순위(대기열 새로고침)_

- 대기열을 만드는 것은 **프론트에서 작업**하고 결과물이 백엔드로 들어옴 → 백엔드에서는 대기열을 고려하지 않음.
- 다른 시스템·사이트에 들어가 새로고침하면 순번이 다시 시작됨. 멘토 생각으로는 **새로고침 시 순번을 유지시켜 줄 수는 없는 것**으로 알고 있으며, 프론트에서 해주는 부분이라 백엔드 관점에서 답해줄 수 있는 것이 없음.

### 1-7. 부하 테스트 방법론

_준비 질문 목록엔 없지만 논의 중 나온 답변_

- 정확한 테스트는 **다른 조들이랑 동일한 조건**으로 하는 것: **Ramp-up 60초, VU 2만.** 이 수치만 동일하게 재현할 수 있으면 이슈 없음. (공식 조건: **테스트 유저 20,000명 · 중복 없음 · ramp-up 60s** — [과업-공식-QnA.md](./과업-공식-QnA.md) 3-3)
- 로컬에서 API를 서버에 올려두고 로컬에서 부하 테스트해서 된 것이라면 **차라리 로컬에서 진행해도 됨.**
- 몇 초 안에 끝났다는 식의 **처리 속도를 보려는 게 아니라**, **60초 안에 2만 건을 동시에 요청했을 때 이슈(과발급·오발급)가 없는지**를 보는 게 가장 큰 목표.
- 안 되면 굳이 AWS에 올리지 않아도 됨. **동일한 조건에서 할 수 있는지만 체크**하고 적용하면 됨.
- 누락을 방지하기 위해 **VU 20,100건** 정도로 설정해 우회하는 방식은, 최소 조건이 2만 건이니 적절하게 설정하면 됨.

## 2. 평가 질문

준비했던 평가 질문 중 **적재 속도 가산점 / 서킷 브레이커 / 대용량 추가 검증 / 채용 과정 평가**는
이 자리에서 답을 받지 못했다(운영·심사 측 공식 답변은 [과업-공식-QnA.md](./과업-공식-QnA.md) 참고).
2차 준비 목록의 `후순위 질문` 1~4도 시간상 다루지 못해 원문만 [질문-원문.md](./질문-원문.md) 에 남겨 뒀다.
실제 답변을 받은 것은 아래 하나다.

### 분산 환경에서 백엔드 엔지니어가 가장 주의 깊게 학습·고민해야 할 핵심 개념

**멘토 답변:**
- 대용량 트래픽에서 **한 건이라도 쿠폰이 잘못 발급되거나 한 사람에게 2개가 발급되면 안 됨.** Kafka/Redis/DB 이슈가 있었을 때 **최종적으로 데이터 정합성을 어떻게 맞출지** 계속 고민하고, 테스트로 현상을 재현하며 방어책을 마련하면 안정적인 서비스가 됨.
- DB가 일시적으로 이슈가 있어도 **서비스가 끊기지 않게 Redis로 즉시 응답**은 했지만, DB 정합성을 가져야 하므로 **DB 후처리를 어떻게 할지**, Kafka 메시지 발행이 안 됐거나 수신하지 못했을 때 **최종적으로 DB 정합성을 어떻게 맞출지** 고민이 필요.
- 스케줄링 도입처럼, **최종적으로 데이터 정합성을 맞출 수 있는 방법**을 고민하는 게 좋음.
