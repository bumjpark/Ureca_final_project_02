## 1. 멘토가 먼저 짚은 지적사항

### 1-1. `coupon_policy.issued_quantity` 컬럼은 정책 테이블에 두기 부적합

- ERD의 `coupon_policy`(쿠폰 정책) 테이블은 고정값 성격인데, `issued_quantity`처럼 **계속 증가하는 값**이 정책 테이블 컬럼으로 있어야 하는지 의문.
- 실제 발행 횟수는 **발급 이력 쪽에서 집계**하는 게 데이터 관점에서 자연스럽다.
- → **결론: 컬럼 삭제** (아래 2-1 조사 결과 참고)

### 1-2. `updated_at` 은 넣을 거면 전부 넣어라

- 실무에서는 `created_at` / `updated_at` + 생성자 ID / 수정자 ID 를 이력 파악 목적으로 **모든 테이블에 기본 탑재**한다.
- 현재 `coupon_policy`, `coupon_issue`, `*_log` 등 일부에만 `updated_at`이 있음 → 넣을 거면 일관되게 전부 넣을 것.
- → **결론: 누락된 테이블에 `updated_at` 추가** (아래 2-2 조사 결과 참고)

### 1-3. Reconciliation 스케줄러 — Kafka 지연분과의 중복 저장 주의

- 핵심 아키텍처 [2단계]: 1분마다 누락 검증 후 DB 미반영 건을 Kafka 재발행.
- 이때 **"DB 조회 시점엔 미반영이었는데, 그 직후 원래 Kafka 메시지가 뒤늦게 도착해 DB에 반영"** 되는 케이스가 있으면 같은 발급이 **중복 처리**될 수 있다.
- → 컨슈머(또는 브로커) 쪽에서 **"이 메시지를 이미 수신·처리했는지" 확인하는 패턴**(인박스 패턴)이 필요. (아래 `3장 3순위` 참고)

### 1-4. 대기열 진입은 시스템 처리 한도의 70~80% 내에서 조절

- 처리 가능한 rate 한계는 기본적으로 존재한다. 대략 **70~80%** 를 기본값으로 두고 크게 흔들지 않는 편.
- 그 한도 내에서 대기열 진입을 적절히 조절하면 괜찮다. (아래 `3장 4순위` 참고)

## 2. 지적사항 후속 조사 결과

### 2-1. `issued_quantity` 컬럼 조사

`coupon_policy.issued_quantity` (`V1__init_schema.sql:49`, 코멘트: "현재 DB 발급 완료 수량 (배치 집계용)")

| 구분 | 현황 |
| --- | --- |
| **쓰는 곳(write)** | `CouponPolicy.java:91-92` `syncIssuedQuantity()` 세터가 있으나 **호출처가 프로젝트 전체에 0곳.** 생성자에서 `0`으로 초기화된 뒤 그대로 방치 |
| **읽는 곳(read)** | `CouponPolicyResponse.from()`이 `getIssuedQuantity()`를 API 응답에 그대로 담음 → `POST/GET /api/admin/coupon-policies` 응답의 `issuedQuantity` 필드 (UBM-13 목록/상세조회에서도 노출) |

**→ 지금 이 API를 호출하면 `issuedQuantity`는 항상 `0`.** 갱신 로직 자체가 없음.

실제 발급 수량은 이미 두 군데서 각자 계산 중:
- **UBM-15 실시간 발급현황** (`CouponStatusService`): `totalQuantity - Redis 실시간 재고`로 즉석 계산 (컬럼 미사용)
- **D그룹 검증배치** (`VerificationAsyncTrigger.java:130`): `coupon_issue` 테이블 실제 row 수(`dbUserIds.size()`)로 즉석 계산 (컬럼 미사용)

`issued_quantity`는 "캐싱해두자"는 의도로 설계됐으나 두 기능 다 실시간/배치 계산으로 가면서 갱신 로직이 빠진 채 방치된 것으로 보임.

**조치: 삭제** — 컬럼 + 엔티티 필드 + `syncIssuedQuantity()` + `CouponPolicyResponse.issuedQuantity` 필드 제거.
단, `CouponPolicyResponse`는 공개 API 응답 스펙이므로 프론트/타 조에서 이 필드를 참조 중인지 먼저 확인 필요 (오너: 박종범, UBM-13).

### 2-2. `updated_at` 컬럼 현황

| 엔티티 | `createdAt` | `updatedAt` | 생성 후 수정됨? |
| --- | :---: | :---: | --- |
| `CouponPolicy` | ✅ | ✅ | 예 |
| `CouponIssue` | ✅ | ✅ | 예 |
| `ReconciliationLog` | ✅ | ✅ | 예 (재처리 상태 갱신) |
| **`VerificationReport`** | ✅ | ❌ | **예 — 그런데 컬럼이 없음** |
| `User` | ✅ | ❌ | 아니오 (생성 후 수정 없음) |
| `CouponHistory` | ✅ | ❌ | 아니오 (append-only 이력 로그) |

**조치: `VerificationReport`에 `updated_at` 추가.** `User` / `CouponHistory`는 성격상 불변이지만, 멘토 조언대로 일관성을 위해 전 테이블 추가도 검토.

## 3. 질문별 멘토 답변

> 준비 질문 **5순위(전체 시스템의 다음 병목) · 7순위(운영 DB 부하 없는 검증) · 8순위(쿠폰 취소 정책)** 는
> 1차에서 답을 받지 못해 생략한다.

### 1순위. Redis Lua의 병목 가능성

- 멘토도 이 규모의 트래픽을 직접 다뤄본 적은 없음. 지인 사례로는 Lua 스크립트를 썼고, 내부에서 GET/SET 대신 **INCR/DECR로만 처리**했다는 정도만 전해 들음.
- **Lua 스크립트의 주의점: 롤백이 안 된다.** 중간에 오류가 난 상황을 가정해 대응이 준비돼야 함.
- 아무리 원자성을 보장해도 대용량 트래픽이면 어느 정도 병목은 생길 수 있음. 문제가 되면 **Lua 안의 로직을 줄이거나 다른 방안**을 찾아야 함.
- **판단 기준:** 우리 시스템의 목표치를 정하고, 그 성능에 도달하지 못하는 원인이 Lua 내부 실행이라고 판단되면 그때 다른 기술을 고려.
- 현재로서는 Lua 자체가 병목이다/아니다를 단정하기 어렵다 → **테스트로 확인.**

### 2순위. Redis ↔ DB 정합성

- Redis 정합성이 깨진 경험은 없었음. 다만 **Redis가 다운돼 요청이 DB로 바로 유입되면서 문제가 생긴 적**은 있음.
- Redis는 **캐싱 저장소**이므로 **DB가 우선**돼야 함.
- Redis가 복구됐을 때 DB와 정합성을 다시 맞추는 시점이 문제. **규약을 어떻게 정하느냐**에 따라 다름:
  - "Redis가 발행한 것을 우선으로 하겠다"
  - "Redis는 무시하고 DB를 기준으로 재처리하겠다"
- **권장 방향:** Redis가 다운되면 **Redis에서의 신규 유입을 막고**, **Kafka에 남은 것을 DB로 모두 처리한 뒤**, **DB를 Redis에 동기화**하는 방식으로 진행해도 될 것.

### 3순위. Kafka Consumer 장애 대응

_지적사항 1-3 과 연결_

- Reconciliation 스케줄러가 다시 돌면서 **Kafka 재발행 요청이 2번 발생**해 컨슈머가 같은 요청을 두 번 받는 상황 → **컨슈머 쪽에서 처리**해야 함.
- Kafka가 발행하는 **요청 ID에 대해 컨슈머가 "이건 처리했다"는 기록**을 남겨야, 재발행돼도 같은 처리를 반복하지 않음.
- → **인박스 패턴**을 보면 비슷하게 구현할 수 있을 것.

### 4순위. 이벤트 순간의 트래픽 스파이크 대응

_지적사항 1-4 와 연결_

- 처리할 수 있는 **rate 한계**는 기본적으로 존재. 대략 **70~80%** 를 기본값으로 주고, 값을 크게 흔들지는 않을 것 같음.
- 그 **한도 내에서 대기열 진입을 적절히 조절**한다면 괜찮음.

### 6순위. 300만 건 정합성 검증

- 보강책을 통해 요구사항(수만 건 이상)도 무리 없이 처리된다면 괜찮겠지만, **워낙 큰 수라 비트연산이 잘 될지 의문** → **테스트로 정상 동작 확인** 필요. 정상 동작하면 그대로 진행해도 됨.
- 기존 데이터 300만 건에 대해 **전수 검증을 한 번 하고 나면 그 이후로는 안 해도 될 것 같음.** 발급됐고 사용 완료·기간 만료돼 **다시 볼 필요 없는 쿠폰 데이터**가 상당수일 것이므로, 이 부분을 **따로 정의**해서 검증 대상을 좁혀도 됨.
- 멘토도 확신은 없음("다 해야 되나 의문") → **현직자 의견도 확인**하면 좋겠다.

### 9순위. 동시 상태 변경 처리 (DB락)

- 실무에서 DB락도 가끔 사용하지만, **지금과 같은 다량의 트래픽에서는 DB락을 선택하지 않는 것**으로 알고 있음.
- 현재 부하 테스트 상태에서 **Redis 안 쓰고 DB락을 걸어 테스트**해보면, 커넥션 타임아웃이 나거나 걸리는 시간·오류가 많이 날 수 있음 → 직접 돌려보면 됨.
- **트래픽이 없는 상황**(요청이 많지 않을 때)에서는 DB락을 걸어 사용하기도 함.

### 10순위. 대기열 새로고침

- 대기열은 **프론트엔드 영역**이라 백엔드 관점에서 답변할 내용이 제한적. 다른 사이트도 새로고침하면 순번이 다시 시작되며, 멘토 생각으로는 **새로고침 시 순번을 유지시켜 주기는 어려운 것**으로 알고 있음.
- **선착순 기준을 어디에 둘지**를 팀이 정해야 함:
  - **대기 순번을 받는 것 자체**가 선착순 기준 → 대기 토큰 발급 시 부여한 순번을 **쿠폰 발급 요청까지 그대로 들고 가야** 함.
  - **대기열은 대기열이고, 쿠폰 발급 요청 시점**이 주된 순번 → **현재 구조 그대로** 하면 됨.

## 4. 준비 질문 외에 나온 답변

### 4-1. 검증 리포트 형식

- **사용자별로도 볼 수 있어야 한다.** 잘못 발급된 게 있으면 **어떤 사용자에 의해 발생했는지** 정보가 같이 들어가 있어야 리포트 양식에 맞음.
- 검증 결과가 **원인별로 분류**되면 분류해서 작성하는 게 보기 좋음.
- 총합 숫자 하나만 주면("몇 건이 안 맞아요") 왜 불일치했는지·초과발급이 몇 건인지 **내부 이력을 다시 확인**해야 함 → 애초에 **원인을 별도로 상세하게** 적을 수 있으면 좋음.

### 4-2. 선착순(FCFS) 검증 방법

- 선착순 검증을 실무에서 해본 적이 없어 정답은 못 줌.
- 적어준 대로 **당첨자 명단만 확인해도 충분**하지 않을까. "이론상 당첨자(요청 도착 순 앞 N명)"와 "실제 확정 당첨자" **두 집합만 비교**하면 됨.
- 나중에 추가 요청으로 "정확하게 순서를 찍어라" 하면 순서대로 명단을 전수 확인해야 하지만, 그 정도가 아니라면 집합 비교로 충분.

### 4-3. 도착 순번 기록

- Redis에 **몇 번째 도착인지 순번을 붙여보고**, 붙이지 않았을 때와 **유의미한 차이가 있는지 확인**해보는 것도 좋음.

### 4-4. Redis 장애 실측 테스트

- 처리 자체가 대용량 트래픽이라 Redis가 부하를 받는 건 맞지만, **복구 직후의 더 큰 부하가 정말 문제 될지는 미지수** → 일단 **테스트를 해보는 게 좋음.**
- Redis를 중간에 한 번 죽이고 다시 살려서 **정상적으로 살아나는지 직접 확인.**
- 기존에 Redis가 들고 있던 상태까지 복구할 거라면 몇 가지 설정이 필요:
  - Redis가 죽을 때 **파일을 떨궈(AOF 등) 그 파일 기점으로 복구**
  - Redis 재기동이 오래 걸린다면 **레플리카**를 둬서 운영
- 테스트해보고 결정하면 좋음.

> 공식 과업 Q&A(프로젝트 범위·Mocking 범위·부하 조건·평가 기준 등)는 [과업-공식-QnA.md](./과업-공식-QnA.md) 참고.

## 5. 후순위 / 추가 질문 (평가·운영 관련)

### 추가 Q1. 큐 소진 실패로 인한 전산 장애 경험

- 다량 요청 + 별도 큐(엔큐) 사용 환경에서 **큐가 소진되지 않아 큐 시스템이 다운**되며 전산 장애가 난 적 있음. 트래픽이 아주 많진 않았지만 큐가 안 빠지면서 다운.
- 한 시스템(A)의 응답이 느려지면 **전체 시스템이 느려지고** 전산 장애로 번짐. 잘 되다가 안 되는 경우도 있음.
- 장애 발생 시 대응: ① 최근 수정 배포 내용 확인 → ② 다량 트래픽의 출처 확인, **DDoS 여부 확인** → ③ 일반 트래픽이면 원인 분석 + 개선점 논의 → ④ **지속되면** 어딘가 문제가 있는 것이므로 협업 서비스와 함께 진행. 원인은 매우 다양.

### 추가 Q2. 트래픽이 지금보다 더 늘면 어떻게 대응할지

- 기존보다 **더 많은 요청**, **더 짧은 시간에 많은 요청** 넣어보기.
- 애플리케이션을 **2대 이상 띄워 HA(고가용성)** 고려.
- Redis·앱 장애 시 **우리의 대응 방식**과 **데이터 처리 방식**(예: Kafka 메시지를 모두 소비한 뒤 DB에 반영)을 미리 설계.
- 기본 요구사항을 만족하면서 개선사항을 생각하면 좋음.

### 추가 Q3. 서버 다중화

- 먼저 **서버 다중화**. 멘토 환경은 애플리케이션 서버 / DB 서버 / Redis 서버를 분리하고 **각 서버를 2대씩** 운영.
- 다중화하면 고려할 게 많아짐: **DB 간 싱크**를 어떻게 맞출지, 앱 2대가 **각각 처리하는 내용이 안 맞는 경우** 등.

### 추가 Q4. 병목 지점 파악

- 선착순 경험은 없지만, 신규 오픈 시 예상보다 많은 트래픽이 와서 서버 부하가 생기면 **어느 쪽에서 병목이 일어나는지, 개선점이 있는지**를 이야기하게 됨.
