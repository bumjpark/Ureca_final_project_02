## 1차 멘토링 준비 질문

### 1순위. Redis Lua의 병목 가능성

Redis Lua를 통한 원자적 재고 차감이 트래픽 증가 시 새로운 병목이 될 가능성이 궁금합니다.

현재는 Lua Script를 통해 재고 차감의 원자성을 보장하고 있는데, Redis는 단일 스레드 기반으로 Lua Script 실행 중 다른 요청의 처리가 지연될 수 있다고 이해하고 있습니다.

그렇다면 현재 구조가 결국 분산 락을 Redis의 직렬화 처리로 대체한 형태가 될 수 있는지, 그리고 트래픽이 현재 테스트 규모의 10배 이상 증가했을 때 Redis Lua가 실제 병목이 될 가능성과 이를 판단하기 위해 어떤 지표를 확인해야 하는지 궁금합니다.

### 2순위. Redis ↔ DB 정합성

Redis에서 재고를 차감한 이후 Kafka Consumer 또는 DB 장애로 영속화에 실패하는 경우, Redis와 DB 간 정합성을 어떻게 보장하고 복구하는 것이 실무적인지 궁금합니다.

예를 들어 Redis에서는 쿠폰 재고가 차감되었지만 Kafka Consumer가 장애를 일으켜 DB에 발급 이력이 기록되지 않는 상황을 고려하고 있습니다.

실무에서는 이를 보상 트랜잭션, 재처리, 멱등성, 정합성 검증 배치 등의 방식 중 어떤 조합으로 해결하는지 궁금합니다.

### 3순위. Kafka Consumer 장애 대응

Kafka Consumer가 메시지를 처리하는 도중 비정상 종료되거나 재시작되는 상황에서 쿠폰 발급의 정확성을 어떻게 보장하는지 궁금합니다.

특히 메시지가 중복 소비되거나 처리 중 장애가 발생할 수 있는데, 실무에서는 Consumer의 재처리와 DB의 멱등성 보장 중 어느 계층에서 최종적인 중복 처리를 방어하는지 궁금합니다.

### 4순위. 이벤트 순간의 트래픽 스파이크 대응

실제 선착순 이벤트처럼 특정 시점에 트래픽이 순간적으로 급증하는 상황에서는 어떤 계층을 가장 먼저 방어하는지 궁금합니다.

현재 테스트에서는 워밍업 이후 부하를 발생시켰지만, 실제 서비스에서는 이벤트 시작 순간 트래픽이 급격하게 증가할 수 있습니다.

이 경우 Tomcat Thread Pool, HikariCP, Redis, Kafka 등의 각 계층에 어떤 방어선을 두는 것이 일반적인지, Rate Limiting이나 대기열을 어느 단계에 적용하는 것이 효과적인지 궁금합니다.

### 5순위. 전체 시스템의 다음 병목

현재 구조에서 Redis를 통해 재고 차감 병목을 줄이고, Kafka와 Batch Insert를 통해 DB 쓰기 병목을 분리했는데, 그렇다면 트래픽이 더 증가했을 때 다음 병목은 어느 계층에서 발생할 가능성이 높은지 궁금합니다.

Redis CPU/메모리, Kafka Broker 및 Partition, 네트워크 I/O, DB Batch Insert 등 여러 후보가 있을 때 실무에서는 어떤 지표를 기준으로 병목 지점을 판단하는지 궁금합니다.

### 6순위. 300만 건 정합성 검증

대규모 데이터의 정합성을 검증할 때 어느 수준까지 자동화하는 것이 실무적으로 적절한지 궁금합니다.

현재 약 300만 건 규모의 데이터를 대상으로 SQL 집계 및 비교를 통해 정합성을 검증하려고 하는데, 단순 집계 쿼리만으로 충분한지 아니면 Spring Batch 등의 별도 검증 프로그램을 구성하여 정합성 검증 결과를 리포트 형태로 남기는 것이 일반적인지 궁금합니다.

### 7순위. 운영 DB에 부하를 주지 않는 정합성 검증

운영 중인 대규모 DB의 정합성을 검증해야 할 경우, 검증 작업으로 인해 운영 트래픽에 영향을 주지 않으면서도 정확성을 확보하기 위해 실무에서는 어떤 방식을 사용하는지 궁금합니다.

Read Replica, 스냅샷, 배치 처리, CDC 등의 방법 중 어떤 방식을 상황에 따라 선택하는지 궁금합니다.

### 8순위. 쿠폰 취소 정책

쿠폰의 발급 → 사용 → 취소 상태 전이를 설계할 때 실무에서는 취소된 쿠폰을 기존 발급 건의 상태 변경으로 처리하는지, 아니면 기존 쿠폰은 취소 상태로 유지하고 새로운 쿠폰 발급 건을 생성하는지 궁금합니다.

또한 취소로 인해 재고가 반환되는 정책이라면, 반환된 재고를 기존 대기열의 다음 사용자에게 자동으로 배정하는 방식이 일반적인지도 궁금합니다.

### 9순위. 동시 상태 변경 처리

발급·사용·취소와 같이 동일한 쿠폰의 상태 변경 요청이 동시에 발생할 수 있는 경우, Kafka를 통한 순차 처리와 DB의 Optimistic/Pessimistic Lock 중 어느 계층에 더 강하게 의존하여 데이터 무결성을 보장하는 것이 적절한지 궁금합니다.

또한 실무에서는 메시지 순서 보장과 DB Lock을 함께 사용하는지, 아니면 특정 계층에서 책임을 집중시키는지도 궁금합니다.

### 10순위. 대기열 새로고침

사용자가 대기열에서 대기하는 동안 페이지를 새로고침하거나 재접속하는 경우에도 기존 대기 순번을 유지하고 다시 조회할 수 있도록 설계했는데, 이러한 방식이 실무적인 대기열 UX 및 서버 설계 관점에서 적절한지 궁금합니다.

## 2차 멘토링 준비 질문

1. 선착순 정합성 검증을 체크섬 스크리닝 → 상세 diff 2단계로 설계했는데, 실무에서 이런 운영을 해보셨다면 실제로는 어떤 방식을 쓰시는지?

2. RESERVED/ISSUED + 스케줄러 복구 구조에서, 실무에서 이런 중간 상태를 관리할 때 흔히 터지는 함정이 무엇인지? (스케줄러가 복구 중인데 원래 컨슈머도 늦게 도착해서 이중처리되는 경합 같은 게 있는지)

3. 동시성 제어를 Redis 원자성 + Kafka 순서 보장으로 설계했는데, DB락(비관적/낙관적 락)과 비교했을 때 실무에서는 어떤 기준으로 선택하는지? DB락으로 이런 트래픽을 처리해본 경험이 있는지?

4. Redis-DB 정합성이 깨졌을 때 대응으로 스케줄링 재처리 + 검증 배치 + 수동 재처리 API 조합을 검토 중인데, 실무에서 실제로 운영해본 조합은 뭐였고, 그중 실제 장애 때 진짜로 동작했던 건 뭐였는지?

5. 검증 결과를 원인별(존재 불일치/카운터 누수/이력 불일치/초과발급 등)로 나눠 DB에 저장할지, 총합 숫자 하나 + 별도 CSV 상세 리포트로 나누는 방식으로 충분한지? "이력-재고 불일치 0건"이 핵심 평가 지표인데 실무에서는 어떻게 저장하는 게 일반적인지?

6. 선착순 검증을 "누가 당첨됐는지"까지만 볼지 궁금 — "요청 도착 순서대로 앞에서부터 N명(이론상 당첨자)"과 "실제 당첨자"를 비교하는 방식으로 설계했는데, 당첨자들 사이의 내부 처리 순서까지는 확인이 안 됨. 실무에서는 이런 선착순 검증의 정밀도를 어느 수준까지 요구하는지, "당첨자 명단이 맞는지"만 확인해도 충분한 편인지?

7. 도착 순서 확인을 위해 트래픽이 가장 몰리는 순간에 Redis에 검증용 기록(몇 번째 도착인지)을 추가로 남겨야 하는데, 이런 "검증/관측 목적의 부가 기록"을 트래픽에 영향 없이 붙이는 다른 방법이 실무에 있는지?

8. 대기열 진입 시 ZADD, 재고 차감, activeToken 저장을 Lua Script 하나로 묶어 원자성을 보장했는데, 실무에서는 Redis Transaction(MULTI/EXEC)과 Lua Script 중 어느 것을 더 선호하는지, 그 이유는?

9. 같은 배치(Batch) 안에서 뽑힌 유저들 사이의 미세한 순서 역전을 감안해 "배치 경계선 새치기는 불가"를 핵심 보장 기준으로 설계했는데, 현업에서 "순서 공정성"의 기준을 어디까지 잡는지?

10. 대기열 진입 시 Redis가 순간적으로 다운되면 유저가 재시도하는데, 이 재시도가 몰리면서 Redis 복구 직후 더 큰 부하를 받는 문제를 어떻게 방어하는지?

### 후순위 질문

1. 이런 이벤트성 트래픽 시스템에서 실제로 장애를 겪은 적이 있다면, 원인이 뭐였고 그 뒤로 어떻게 바꿨는지?

2. 20,000 요청 / 초과발급 0건 같은 수치 말고, 실무자가 봤을 때 "이건 고민했네" 싶은 어필 포인트가 저희 프로젝트에서 뭐라고 보는지?

3. 저희가 구현한 시스템을 실무 수준으로 개선한다면, 가장 먼저 바꿔야 할 부분이 어디라고 보는지?

4. 실제로 선착순 이벤트를 운영해봤다면, 예상 트래픽과 실제 트래픽이 얼마나 차이가 나는지, 트래픽 예측이 빗나갔을 때 대응은 어떻게 했는지?
