🚨 1. 동시성 제어 (Race Condition)
  • 10,000장 재고에 20,000건 동시 인입
  • 두 요청이 동시에 재고를 읽고 차감하는 경합 발생
  • 재고 초과 발급(Over-selling) 0건 절대 보장
  • NFR-1 최우선 정합성 지표 수호
🔒 2. 엄격한 1인 1매 제한
  • 광클, 새로고침(F5), 멀티 탭, 봇 차단
  • 동일 유저의 동시 다중 요청 무효화
  • 1명의 유저가 여러 장을 가로채는 어뷰징 방지
  • 식별자 기반 초고속 원자적 중복 판정 필요

현업 시스템 조사와 의문: "왜 Redis + Kafka인가?"

남들이 쓰는 기술을 맹목적으로 따르지 않고 실측으로 증명하기로 한 이유

1. 현업 서비스 조사 (배민, 무신사, 인터파크 등)
• 대규모 트래픽 기업들의 공통 아키텍처: "Redis (인메모리) + Kafka (메시지 큐)"
• 순간 폭주 트래픽을 인메모리에서 걸러내고, DB 저장은 비동기 큐로 완충하는 표준 패턴 확인
2. 팀의 엔지니어링 의문 (Why?)
• "남들이 쓴다고 무작정 도입하는 것은 엔지니어링이 아니다."
• 왜 Java 락이나 DB 락으로는 안 될까? 단순 Redis 명령어로는 왜 동시성이 터질까?
• Kafka만 도입하면 정말 무조건 빨라지는가? 실제 병목은 어디에 있는가?
3. 가설과 실측 기반의 8단계 검증 여정
• 가장 원초적인 순수 Java(락 없음)부터 DB 비관적 락, Redis Lua, Kafka Consumer 최적화까지
• 각 대안에 20,000건 부하를 직접 걸어 한계를 깨뜨려보고, 수치로 증명하며 최적의 아키텍처를 도출하기로 결정

4~5차 테스트: Redis 도입과 Lua Script의 원자성

Check-then-Act 문제 해결과 분산 락 없는 초고속 동시성 제어

❌ 단순 Redis DECR의 실패 (4차)
  • GET(재고조회) ➜ SISMEMBER(중복체크) ➜ DECR(차감) 분리 호출
  • 명령 사이의 미세한 시간 차로 인해 동시성 침투
  • 실측 결과: 60,000건 요청 시 6,646건 중복 발급 발생
  • 결론: 개별 명령어 호출만으로는 원자성 보장 불가
✅ Redis Lua Script (EVAL) 적용 (5차)
  • SCARD + SISMEMBER + SADD를 단일 스크립트로 통합
  • Redis 싱글스레드에서 단 1회의 트랜잭션으로 원자 실행
  • 별도 분산 락(Redisson) 대기 시간(RTT) 0초 달성
  • 실측 결과: 60,000건 동시 요청 시 초과발급 0건, 877ms 마감

6차 테스트: Redis + 동기 DB 저장의 병목

Redis는 1ms인데 왜 전체 처리는 12.7초가 걸리는가?

📊 실측 데이터 비교 (Redis 판정 vs 동기 DB 저장)
• Redis Lua 판정 시간 : 1 ms 미만 (초고속 승인)
• 전체 소요 시간 : 12,706 ms (12.7초, 심각한 지연)
• 가장 오래 걸린 DB 저장 대기 시간 : 7,413.41 ms
🔍 병목 원인 분석 & 엔지니어링 결론
1. DB 커넥션 풀(HikariCP 10~20개)이 순간적으로 몰리는 2만 건의 동시 쓰기 요청을 감당하지 못함.
2. 서버 스레드가 DB INSERT 완료를 기다리느라 블로킹되어 뒤쪽 요청들이 도미노처럼 큐잉 지연 발생.
3. 핵심 결론: "발급 승인 응답(동기)"과 "DB 영속화(비동기)"는 반드시 아키텍처적으로 분리되어야 함.

Kafka Consumer 최적화: SEQUENCE 채번 & JDBC Batch

DB 쓰기 처리량 5.5배 폭발적 개선 (229 TPS ➜ 1,250 TPS)

1. IDENTITY ➜ SEQUENCE 채번 전략 전환 (V7)
MySQL IDENTITY는 ID 조회를 위해 매 save마다 즉시 flush를 강제함 ➜ SEQUENCE 메모리 사전할당(allocationSize=50)으로 트랜잭션 종료 시 일괄 flush 달성
2. JDBC Batch Insert 활성화
rewriteBatchedStatements=true 설정으로 수백 개 개별 INSERT 쿼리를 단 1개의 Multi-Row Bulk INSERT 문으로 압축 전송
3. 100건 청크 트랜잭션 & Fallback 격리
정상 건은 100건 청크 단위 일괄 처리(processChunk), UNIQUE 위반 발생 청크만 건별(processSingle)로 안전하게 폴백 격리
🚀 개선 결과 : DB 영속화 시간 43.6초 ➜ 8.0초 (DB 처리량 229 TPS ➜ 1,250 TPS, 5.5배 향상 / 드롭 0건)

트래픽 폭주와 네트워크 유실: 대기열 도입의 계기

로컬 OS 소켓 한계와 Thundering Herd 극복

⚠️ 대규모 부하 테스트 중 마주한 네트워크 레벨의 병목
1. 소켓 연결 거부 (Connection Refused 29.77% 발생)
• 2만~10만 가상 유저가 0초에 동시 인입되면서 OS의 TCP 소켓 포트(65,535개) 고갈 (TIME_WAIT)

• 진입 대기 중인 유저들이 불안감으로 F5를 연타하여 수만 건의 중복 요청이 쏟아짐

동적 스케일링 대기열 & SSE 실시간 통보 아키텍처

ZPOPMIN 원자적 추출 + 파이프라이닝 토큰 발급 + Server-Sent Events 푸시

1. 대기열 등록 (/queue/join) & 멱등성
Redis ZSET(Score=timestamp)에 순번 등록. F5 연타 시에도 ZSCORE로 기존 순번을 멱등하게 유지하여 중복 줄서기 차단
2. 분산 락 기반 입장 스케줄러 & 동적 자동 스케일링
1초 주기 QueueAdmissionScheduler가 다중 서버 중 분산 락(SETNX) 획득 후, 대기열 부하에 따라 QueueLimitAdminService로 입장 정원을 자동 스케일링
3. 원자적 추출 & 파이프라이닝 토큰 발급 (ZPOPMIN)
Math.min(batchSize, stock) 정밀 슬라이싱 후 ZPOPMIN으로 선두 인원을 원자적 추출하고, Redis Pipelining으로 60초 TTL activeToken 일괄 등록
4. SSE(Server-Sent Events) 실시간 토큰 푸시 & 보안 검증
클라이언트 폴링 부하 없이 SSE 스트림으로 activeToken을 실시간 전달 ➜ /issue 요청 시 토큰 소유자(userId) 일치 여부를 원자적으로 소비/검증하여 매크로/우회 100% 차단

선착순 공정성 & 5대 역전 시나리오 완벽 방어

배치 내 미세 역전 허용 vs 경계선 새치기 0% 차단

상황 / 시나리오 역전 발생 여부 공정성 및 시스템 영향 적용된 방어 기술 / 원리
1. 대기열 줄서기 ❌ 역전 불가 (0%) 먼저 도착한 패킷이 무조건 낮은 순번 수령 (100% 공정) Redis 싱글스레드 + INCR 단조 증가
2. 동일 배치 내 발급 (300명) ⚠️ 미세 역전 허용 300명 모두 당첨 확정 그룹이므로 공정성 피해 없음 activeToken 보유자 그룹 동시 처리
3. 당첨/탈락 경계선 (마지막 10개) ❌ 절대 불가 (새치기 차단) 11등이 10등을 제치고 쿠폰 가로채기 0건 보장 Math.min(batch, stock) 정밀 슬라이싱
4. 60초 타임아웃 만료 ⭕ 정상 추월 (정책적) 잠수 유저 슬롯을 다음 대기자에게 자동 양도 activeToken TTL + EXPIRED 만료 마커
5. 서버 다중화 (서버 A, B) ❌ 역전 불가 서버 N대 분산 환경에서도 단일 시퀀스 보장 중앙 집중형 Redis ZSET 시퀀스

시스템 장애 격리 & 5계층 방어 로직

어느 레이어가 터져도 서비스는 중단되지 않는다

1계층: 유입 제어 (API Gateway & Redis ZSET)
소켓 폭풍 방어, F5 중복 줄서기 차단, activeToken 우회 차단
2계층: 메모리 검증 (Redis Lua & 2-State)
0.5ms 만에 400 Fast-Fail, DB 트래픽 99% 차단, 1인 1매 엄격 보장
3계층: 비동기 완충 (Apache Kafka Broker)
policyId+userId 파티션 키로 순서 보장, DB 지연 흡수, DLT 격리
4계층: 자가 치유 (ReconciliationScheduler)

Part 3. 실전 트러블슈팅

Redis 완전 유실 장애 복구 & Kafka Lag 안전 방어선

부하 도중 FLUSHALL(전멸) 발생 시 SSOT(MySQL) 기반 원자적 복원

💥 극단적 카오스 테스트: 부하 도중 Redis FLUSHALL 강제 주입 (T = 32s)
• 장애 상황: 4,557건 발급 완료, Kafka에 4,311건 처리 중, 잔여 재고 5,443건인 시점에 Redis 완전 삭제

🛡️ 안전 복구 메커니즘 (RedisRecoveryService)
1. Kafka Lag 안전 방어선 : 컨슈머 랙(Lag > 0) 존재 시 섣부른 복구 시도를 409 Conflict로 즉시 차단 ➜ 중복 발급 원천 방어
2. Lag = 0 도달 시 SSOT 복원 : MySQL 실제 저장량(4,557건) 기준으로 잔여 재고(5,443개) 및 발급자 SET 116ms 만에 원자 재구성
✅ 최종 정합성 검증 결과 : DB 발급(4,557) + Redis 잔여(5,443) = 정확히 10,000장 보존 (PASS), 중복 0건, 감사 로그 100% 일치
Part 4. 300만 건 정합성 검증

300만 건 정합성 검증: 체크섬의 한계와 집합(Set) Diff 아키텍처

단순 카운트 비교를 넘어선 대규모 데이터 무결성 검증 설계

❌ XOR 체크섬 방식 검토 및 탈락 사유
• 초기 검토 : 빠른 집계를 위해 BIT_XOR(user_id) 고려

1. 오류 상쇄 (Collision 위험)
서로 다른 두 이상 건이 우연히 같은 체크섬을 만들어 정상으로 오판

2. 중복 자기소멸 (A ⊕ A = 0)
동일 유저가 중복 발급되면 XOR 특성상 0으로 소멸되어 중복 감지 불가!

➜ 결론 : 체크섬 대신 100% 신뢰 가능한 집합(Set) 기반 대조 채택
✅ 최종 채택: Set 기반 양방향 Diff & 불변식 엔진
• 커버링 인덱스 기반 DB 발급자 Set<Long> 추출
• Redis 확정 발급자 Set<Long> 인메모리 로드
• O(N) 양방향 대칭차집합(Diff) 연산 :
  - redisOnly 및 dbOnly 유저 목록 정밀 색출
• 300만 건 대용량 스캔 중에도 메모리 1.45GB 안정 유지
• 이상 발생 시 유저 추적용 CSV 리포트 자동 생성

Q & A

경청해 주셔서 감사합니다. 질문에 성심성의껏 답변드리겠습니다.

Q1. Redis Lua가 싱글스레드인데 트래픽이 10배 늘어나면 병목이 되지 않나요?
A: Lua 연산을 O(1)로 단순화하여 1회 0.1ms 미만입니다. 추가 확장 시 재고 키 샤딩(stock_1, stock_2)과 대기열 동시성 제한으로 CPU 포화를 방어합니다.
Q2. Redis 발급 후 DB 저장이 영구 실패하면 어떻게 되나요?
A: 발급 즉시 RESERVED로 등록되며, DLT 격리와 함께 1분 주기 스케줄러가 60초 초과 미아 건을 DB 확인 후 자동 재발행합니다.
Q3. 300만 건 검증이 운영 DB에 부하를 주지 않나요?
A: 실무 환경은 Read Replica나 CDC 기반 DW에서 검증하며, 본 시스템은 커버링 인덱스와 청크 단위 비동기 배치로 락 경합을 최소화했습니다.
